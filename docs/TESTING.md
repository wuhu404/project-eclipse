## 重要前提（请勿高估以上结果）

- **通关是由脚本机器人完成的，不是人类玩家。** 机器人通过测试钩子注入按键、直接设定瞄准方向（相当于完美瞄准），
  并用导航网格寻路。它验证的是「逻辑链路可以走通」，不是「手感好不好」。
- **机库首战之后机器人开启了无敌。** 机器人不会躲避攻击、也不会去捡血包。关闭无敌（`GOD=0`）时，
  它能打过机库、门禁卡伏击和实验室，但会在工业大厅被重装机器人的迫击炮/砸地击杀。
  因此「不开无敌从头打到通关」**没有被验证**，难度平衡未经人类试玩调校。
- 部分检查用测试钩子传送玩家以缩短流程（如回到靶场、进入机库观察 AI）。

## 未测试 / 无法在本环境验证

- **真人试玩**：射击手感、后坐力、移动手感、关卡节奏、实际通关时长（10–15 分钟是设计目标，未实测）。
- **音频**：测试以静音运行。音频代码执行无报错，但枪声、脚步、音乐的实际听感没有人听过。
- **性能**：本 VM 只有软件渲染，1280×720 下帧时间约 80–90 ms（约 11–12 FPS），不代表真实硬件。
  **没有在任何带 GPU 的机器上测过帧率**，60 FPS 目标未验证。
- **浏览器兼容性**：仅在 Chrome 156 运行过；Firefox / Safari / Edge 未测。
- 困难难度、长时间游玩的内存表现、非 16:9 的超宽屏/小窗口下 HUD 排版。

## 已知限制

- 只有一个关卡；没有手柄和触屏支持，没有按键重绑定。
- 生产构建是单个约 5 MB 的 JS 包（未做代码分割）。
- 敌人与武器模型由基础几何体组合而成，没有骨骼动画；动作为程序化的摆动/后坐/倾斜。
- 敌人寻路基于 0.5 m 的平面导航网格：敌人不会上高架走道，飞行单位不寻路。
- 可爆油桶会被敌人流弹引爆，站在油桶旁边交火有风险。
- `window.__ECLIPSE__` 调试钩子（含无敌、传送）在生产构建中仍然存在。

## 试玩反馈修复记录

### 特效黑块 / 开门后黑块遮挡屏幕

**根因（推断，未能在真实 GPU 上直接复现）**：若干自定义 shader 会输出 NaN——光柱的 `pow(vUv.y, 1.6)`、曳光的 `pow(a, 2.0)` 在 MSAA 下 varying 外插为负数时，真实 GPU 上结果是 NaN；NaN 进入 HDR 缓冲后被 Bloom 的多级模糊扩散成大块黑色。开门后恰好看到下一个房间的光柱，所以表现为"开门后被黑块遮挡"。

**修复**：
- 光柱、曳光、天空、最终合成 shader 中的 `pow` 输入全部钳制，反向 `smoothstep` 改写为定义明确的形式；
- 在 Bloom 之前新增 HDR 清洗通道（`Gfx.ts` 的 `SanitizeShader`），把 NaN / Inf / 负值归零并限幅，任何来源的坏像素都不会再被扩散。

**验证（本机 SwiftShader 软件渲染）**：
- `tests/nan2.mjs`：向光柱注入 NaN / Inf / 负值。清洗关闭 → 整屏变黑（HDR 缓冲 691200 个分量全部为 NaN，与反馈现象一致）；清洗开启 → 坏像素为 0，画面正常。
- `tests/doors.mjs`：从两侧走近并打开门，全程扫描 Bloom 前的缓冲。10 扇门中完成了 7 扇半（15/20 次扫描，其余因软件渲染超时未跑完），坏像素均为 0，截图正常。
- `tests/geoscan.mjs`：561 个几何体无 NaN 顶点、无零长度法线。
- 回归 `tests/e2e.mjs`：第一次 75/76（"Boss 二阶段扫射光束"未出现——Boss 招式随机选择，44 秒的战斗里没抽到，属于测试本身不稳定），重跑 76/76。

**未验证**：本机没有 GPU，原始黑块无法在这里原样复现，修复是否在你的显卡 / 浏览器上完全生效需要你再试玩确认。
